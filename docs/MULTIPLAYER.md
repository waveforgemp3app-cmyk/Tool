# Private shared world

Updated 2026-09-30. This document describes implemented server behavior, not complete original-game parity.

The game requires a registered account or an existing authenticated session. Launcher Sign Up and website registration use the same server. Blank credentials do not open guest play. Older local characters remain explicit sandbox backups and cannot supply trusted levels, inventory or GM privileges.

## Running privately and accounts

### Launcher: local play, Host friends, and Connect

**Start** retains the one-click local world on port 7777. A returning, installed client with a verified current prepared generation shows ready options without a 0/100 preparation bar. Start still checks the original client fingerprint, so changed Global files are imported before play. Missing, malformed, linked, or stale generations do not qualify as ready.

**Host friends** sets up a separate world on port 7778. **Hosting options** offers Invite only or Open; Open removes the invite password but still requires each player to register and sign in. The first time, enter a server name and a new GM account ID/password with confirmation. Invite only also requires a separate invite password; Open does not. Required passwords must be nondefault and at least 12 characters. The optional **Rates** foldout sets EXP, DIL, and drop multipliers from 0.1x to 100x; each defaults to 1x. Setup stores password hashes in private server files and sends credentials through the setup helper's stdin, never command-line arguments. Later Host friends clicks reuse the saved configuration. The protected local installation-owner account and its world are not copied into this world.

The host dashboard's **Host / invite** tab shows a detected LAN/private VPN address and copies it. Send that address and the invite password privately to your friends. If the computer has multiple adapters, select the address on the network your friends can reach. Keep the host dashboard open: closing it saves characters and stops that dashboard's server. Port-specific private controls keep the friends host separate from another local server.

Friends click **Connect**, paste the host address, and click **Test address & connect**. The launcher verifies the limited discovery endpoint, then displays that server name, address, rates, invite password, and Sign In / Sign Up tabs inside the launcher. Create an account there if needed; successful signup clears every field and asks you to sign in. Local Start, Host friends, and each additional client also require native sign-in before opening the game. After authentication, a 45-second one-use opaque ticket transfers the session into an isolated game window. Passwords and cookies never enter the launch URL. The invite cookie is HttpOnly; the password is not put in the URL, browser history, or launcher arguments. Each player needs a separate account. Accounts, characters, shops, GM permissions, and rates belong to that particular host, not every server with this engine.

The browser loads the engine and imported game resources from the chosen host. Joining does not install or clean the friend's game folder. Host only for invited friends who have their own lawful client access; private hosting is not permission to publish or distribute original game assets.

### LAN, VPN, and Internet reachability

On the same private LAN, use the host's private IPv4 address and port 7778. Windows may ask the host to allow Node on **Private networks**. The launcher does not create firewall rules. If discovery fails, check that Host friends is running, both computers use the same LAN/private VPN, the copied address is current, and the host's private-network firewall permits the connection. Guest Wi-Fi isolation can prevent computers from reaching each other.

For friends on other networks, a private VPN that makes the host reachable at a private IPv4 address is a practical first option. Internet hosting requires a reachable **HTTPS** endpoint, TLS termination/reverse proxy, and any needed router/firewall configuration. Connect permits trusted HTTPS server addresses; plain HTTP is restricted to private LAN/VPN or loopback addresses because invite and account passwords travel over that connection. The **Show Internet / HTTPS setup** checkbox is guidance, not a claim that the server is publicly reachable. The optional managed relay described below starts only after explicit configuration and opt-in. The launcher does not configure your domain, tunnel-provider account, UPnP, router, or firewall automatically. A static portal alone cannot run the persistent Node world or its SSE connections.

Store the host's private account/config files securely and back them up. Losing that host's account store does not restore characters from another server. Strong credentials and invite gating reduce accidental access; this is still an unfinished single-process private host, not a managed public service.

The default listener is `127.0.0.1:7777`. The website is `/site/`; the game frontend is `/`. A fresh local account store receives a protected `admin` identity with GM capabilities and a random private password hash; there is no public default password. The installation owner selects **Auto-sign in as local admin** in the launcher. A protected local control file authorizes a short-lived, single-use browser handoff. Password login, forwarded or relayed owner requests, and remote use of owner sessions are denied server-side. The launcher clears credential fields when the owner toggle is selected and hides the toggle for remote worlds. Existing ordinary accounts keep their credentials and permissions; the launcher does not prefill passwords.

A store with a local-only admin marker refuses a non-loopback listener. For a private LAN deployment, use a separate account store and disable local demo initialization before startup, then register your own account:

```powershell
$env:DEKARON_HOST = '0.0.0.0'
$env:DEKARON_LOCAL_DEMO = '0'
$env:DEKARON_ACCOUNT_STORE = Join-Path $PWD 'server/accounts/lan-accounts.json'
node server.mjs
```

Other computers connect to the host's LAN address. Firewall rules are unchanged. HTTP is provided locally; HTTPS, public deployment, account recovery and production operations are separate work. Create separate host/player accounts for this server.

The launcher prepares the owner's client files before starting the server. The selected `.client-cache` manifest chooses the complete generated data; explicit `DEKARON_DATA` and `DEKARON_GAMEDATA` overrides remain available. `DEKARON_ACCOUNT_STORE` chooses the private account JSON file, and `DEKARON_PERMISSION_STORE` chooses host-managed grants. Accounts contain password/session hashes and canonical characters; they are excluded from static serving. Game assets come from the owner's client, while website presentation uses generated illustration and CSS.

Use separate accounts and separate browser profiles for simultaneous clients on one computer. One account has one character lease: another join replaces its earlier lease. This is real connected-player multiplayer, without invented party members or bots.

## Implemented gameplay

- Two-player trading through `/trade Name` and the original trade window. Offers retain original item metadata and require both players to confirm the same revision. Item/DIL transfers commit atomically; failed saves, cancellation, stale offers and replay cannot deliver a duplicate transfer.
- Account-shared storage and DIL. A Storage Keeper's Key unlocks the account feature once. Shared items/currency have one authoritative account record, with original fees, item restrictions, exact destinations and save rollback. Personal storage remains separate.
- Private cross-map whispers and same-map shouts, including mute, recipient and cooldown checks. Guild chat reaches connected members across maps without leaking to nonmembers.
- Character mail through the original windows: compose/read/sent history, offline delivery, one-time item/DIL claims and deletion after attachments are claimed. Original item instance metadata is held in server escrow; sender debit, escrow and collect-quest recount commit atomically in the account store. Recipients do not need to be online. Mail headers are streamed; bodies load on demand. The current 100-DIL postage is an explicit engine policy matching the existing UI, not a verified official-server fee.
- Guild founding uses original level/cost/member limits; invitations, accept/decline, membership, notices, DIL deposits, leadership transfer, kick/leave, zero-fund disband and private guild chat are authoritative. Read/command permissions, pending writes, replay, restart and rename refresh are tested. Original ADV/DIL donations, distinct PlayPoint/GPOINT and explicit guild level-up are supported. Broader ranking/battles and unsupported services stay guarded. Disbanding a guild with funds is refused so funds are preserved.
- Supported original-table crest insert/extract, stone production/crushing, talisman appearance transform/reset and costume wardrobe transfers/equip/unequip/swap now have server routes. Costs/materials/capacity/ownership/NPC roles and exact item metadata are checked before atomic profile saving. UI controls wait for committed results. Unresolved crest definitions/bonus options abort without spending; they are not guessed.
- Successful HP/MP use broadcasts only after persistence. Original recovery effects and item-use audio play once; remote presentation does not run local quest/progression listeners.

- Cookie-authenticated joins, polling and SSE snapshots at roughly 100 ms; lease replacement, logout revocation and server save-failure feedback.
- Original collision/pathfinding and authoritative movement speed, with bounded local visual prediction. Original field gates, level checks, valid arrivals, revival and map-filtered actors.
- Basic combat, monster health/AI/respawn, server EXP/Dil, level stat/skill points and class stat caps. Client HP, damage, rewards and progression snapshots are rejected.
- Original SkillEngine/StatusSystem/SummonSystem running through a private headless adapter: learning, books, learned hotbar assignments, costs, cooldown persistence, combo impacts, buffs and defensive spell/shield rules. Server summons have interpolated original models. Meister path selection, original reinforcement rules, authored Grand Meister rank rewards, and active Trans Up stage/expiry persistence are authoritative. Individual ability effects and animations still need broader verification; three class catalogs currently lack transformation rows and no replacements are fabricated.
- Server inventory/equipment and original starter weapon; item use, shops, D-Shop, bank, loot, reinforcement, sockets, branding, options, conversion and other supported original transactions. Unsupported item services are listed below.
- Original starter quest offering, NPC acceptance/dialog/turn-in, kill/collect objectives, choice rewards, EXP/Dil/items and valid quest warps. NPC identity and proximity, prerequisites, bag capacity and original choices are checked on the server. Inventory mutations recount collect objectives.
- Starter gift and level-up box chain; carried instance ownership, original level/class rules, keys, weighted rolls, selections, capacity and replay rejection. Successful boxes consume the actual instance and return original table rewards. Reconnecting does not regrant the starter kit.
- Seven-member parties using the original party window: create, connected-character invitations, acceptance/decline/expiry, leave, leader transfer, kick, naming and item distribution. Find lists actual connected characters; `/invite name` resolves an exact connected character. Snapshots include member class, map and live HP. Party chat reaches only current members across maps.
- Nearby alive same-map party members receive server kill progress and EXP from the original group ratio table, split equally. Eligibility currently uses a 50-unit radius. Ground loot supports killer/default, turn order, free, random and leader distribution; manual discarded items retain their original owner protection.
- Mounted state from equipped transport slot 20, original summon/dismiss delays and option-43 speed, map/boarding/skill checks and client rider/mount visuals. Mounted basic combat is blocked. Companion pets support original eggs, follow, autoloot, bags, options, blessings and supported awakening items. Original-table pet combination, appearance change, disassembly and restoration use server-owned materials, costs and results. Combination timers survive reconnect; failed saves roll back without reporting success. Remaining mount/vehicle rules and rendered pet-service acceptance still need verification.
- Original-table dungeon admission and isolated runs, Dead Front and Ice Castle cooperative event adapters, authoritative fishing and profession crafting, and DekaPass mission progress/claims are implemented. These reuse available local directors and catalogs; they do not reconstruct unavailable official server scripts or establish all-content parity.
- Host-managed GM permissions, supported command execution and canonical item/quest tools. Signup and browser metadata cannot grant GM. Unsupported GM commands must remain explicit failures.
- Authorized GM player-map destination teleport, online/offline character search and bag/stash inspection. Taking owned items uses exact UID/count and source/destination revisions, server restrictions, atomic ownership/audit commits and durable replay receipts. Failed primary writes retain ownership; intervening ally buffs/progress are preserved, and failed reconciliation remains visibly pending for retry. These are implemented engine administration tools, not a recovered official GM transfer policy; ordinary accounts cannot invoke them.
- Character creation and GM rename share server-validated NFC names up to 30 Unicode code points, spaces/uniqueness rules and a fixed cosmetic color palette. Public snapshots expose supported guild/name/title/grade metadata for literal-text native hover UI; colors cannot grant GM capability or inject markup/styles. Guild crest assignment and earned competitive rank rules remain unresolved; displayed supported metadata does not establish those native contracts.

Dirty profiles are periodically persisted and saved after validated transactions and departure. Failure retains pending state and exposes `self.saveError`. This is a single-process JSON-backed host, not a production database or crash-proof transaction system.

## Protocol

`POST /api/world/join` accepts only `{characterId}` and returns `{token,self,state}`. The authenticated cookie determines the account. `POST /api/world/action` contains `token`, `type` and strictly allowed intent fields. Core types are `move`, `attack`, `travel`, `revive`, `chat`, `allocate`; server service schemas add quests, boxes, inventory/shop/enhancement/conversion, loot, skill, mount and party commands.

Quest commands contain operation/quest ID/NPC/choice, boxes contain owned UID and selected entry indices, and party commands contain operation/connected target ID/name/itemway/text. A client cannot provide a trusted reward list, party roster, resource balance or combat result. Commands and GM requests are serialized per account; server-only catalog and profile rules determine outcomes.

State includes canonical self profile, current-map actors/monsters/summons/drops, party members/connected roster/invitation and recent authorized events. Party chat events are filtered by recipient IDs before delivery. `/api/world/leave` saves and releases the leased character. `/api/world/gm` additionally requires host-managed capability.

## Explicit remaining gaps

Unavailable original server scripts and unsupported quest-objective categories cannot be completed by client claims. Dungeon and event adapters support available original directors and tables, but all dungeon routes, scripted bosses, event phases and quest-objective combinations still require broader gameplay verification. Pet eggs, supported special monster-summon boxes and original-table pet services are implemented; remaining pet/vehicle edge rules and native visual acceptance are separate checks.

Siege, PvP/duels/arenas, rebirth and remaining guild/social/life systems need authoritative implementations. Mail and supported guild operations are listed above; generic automated reward routing, broader guild ranking/battles and fund-bearing disband are not supplied. Remaining item services include D-Shop gifts/payment refill, unresolved crest price/option/bonus semantics and costume sewing/options; supported shape/fabric services use durable original-table transactions. Personal/account-shared storage, two-player trading, ordinary D-Shop purchases/receipts, reinforcement, sockets, branding, amplification, option services and supported conversions are implemented; there is no payment provider. D-Shop wallets and purchases remain character-scoped.

Fishing, profession crafting and DekaPass are authoritative, with canonical persistence and validated reward claims. Unavailable mission hooks and remaining life services are not automatically covered by those ports. Meister ranks use authored quest rewards and prerequisite gates rather than invented automatic level unlocks. Individual Grand/Meister effects, summon targeting/provoke and remote visual parity need further review. Exact native refinement and inventory particle/mesh effects are not fully reconstructed. Map Builder drafts can be published to the shared server with validated revisions, collision, placements and portals. Supported occupied CUSTOM-map revisions use authenticated CAS publication, atomic commit, collision/placement updates, safe relocation and generation-bound reload acknowledgments. Active casts, projectiles, companions, trades, fishing, warps or pending scene/reward transactions explicitly refuse publication. Original-map editing is limited to protected, height-only Ardeca150 updates with shared preview, explicit Save/Cancel and generation-bound acknowledgments. Original collision, scripts, services and water remain protected; other original maps and broader brush operations remain unsupported. Rendered saved-overlay rejoin acceptance is still pending.

## Published maps and host isolation

The map library is stored beside the selected private account store. Publication requires a current GM world lease and a renewed capability check. Archives are bounded and checked before atomic manifest replacement. Ordinary accounts can read published maps but cannot publish drafts or invoke the GM author-entry command. Map entries and archives contain no publisher credentials or private host paths. Original NPC services can be reused in published placements; unsupported service-table substitutions are rejected.

Map publication waits for in-flight commands before checking occupancy; new joins/actions wait until publication finishes. Supported occupied CUSTOM-map revisions use authenticated CAS publication, atomic commit, collision/placement updates, safe relocation and generation-bound reload acknowledgments. Active casts, projectiles, companions, trades, fishing, warps or pending scene/reward transactions explicitly refuse publication. Original-map editing is limited to protected, height-only Ardeca150 updates with shared preview, explicit Save/Cancel and generation-bound acknowledgments. Original collision, scripts, services and water remain protected; other original maps and broader brush operations remain unsupported. Rendered saved-overlay rejoin acceptance is still pending. Shared field portals enforce the map's collision and level limits, and a failed travel save preserves the prior committed scene. Maps reload from the private library after restart.

Hosted original assets and directory listings require an active account session, even on Open servers. Invite-only access additionally requires the invite. Assets use private revalidated caches, and a stale account session cannot obtain a 304 cache response. This access control does not grant distribution rights for the imported content.

Party radius and equal-share policy are explicit engine rules; they are not a reconstruction of an unavailable original server. Large-player sessions, disconnect races, disk-failure recovery, all-map content and sustained GPU/load performance still need broader QA. No complete MMO-parity or universal frame-rate claim is made.

The browser cannot prevent DevTools, DLL injection or automation on another computer. The protection here is server authorization of the implemented actions; it is not a process scanner and does not prevent bots from issuing otherwise valid intents.

## Desktop architecture

The current compiled launcher opens the existing JavaScript game in a browser. A future C++ WebView2 shell could embed that same renderer and authenticated localhost API. That would be a desktop wrapper, not a native C++ gameplay/rendering port; neither is claimed complete here.

### Optional online relay and saved web worlds

Hosting options → More offers an explicit managed HTTPS relay opt-in for either host mode. Supply your managed hostname and a private cloudflared token file; its ingress must target loopback gateway port 7840. This requires an existing managed tunnel configuration and does not configure your domain or router automatically. The original game server binds loopback in this mode. Only after the relay reports readiness can an Open host opt into a selected HTTPS public directory. Invite-only worlds cannot be listed. Registration heartbeats run in an owned helper, and stopping the dashboard opts out and closes the relay. Native fixtures validate ownership and IPC, and temporary public-relay gameplay has been checked. A temporary test tunnel is not a production uptime guarantee; permanent named relay and directory operations require separate configuration.

Connect includes Public Servers for a selected HTTPS directory; it displays compatible Open entries only and rechecks the chosen server before account authentication. No personal directory is baked into the release. Save this web world stores only the verified address in private launcher preferences. On reopening, an asynchronous check can restore a remote dashboard; it has no server-stop permission. Launch desktop client uses an isolated Chromium app window, while Launch browser opens the standard browser. Both choices require native sign-in and a one-use handoff ticket. Local world switches back to local launch. A static website URL without the game API cannot qualify as a connected world.

Private preferences store addresses and managed token-file paths, never account passwords, invite passwords, token contents, or relay secrets. A relay hides the host address from ordinary directory clients; its provider and network infrastructure still handle connection information. Direct LAN or Internet connections do not hide the destination IP.
